## 导读

**一句话结论**：如果重新学一遍 RAG，别从 LangChain、LlamaIndex 或者向量数据库开始，先搞清楚一个问题——一份原始文档，究竟是如何变成大模型最终回答中的一句话的。

**为什么值得看**：这是恩宇三天内的第三篇，直接落在你主线最实的部分。#63 讲模型一层，#64 讲组织一层，这篇讲数据一层——三篇合起来，正好是"模型能做什么、组织能消化什么、数据链路会不会在半路丢东西"。而且它补了上一条里点过名的缺口：记忆/上下文工程。对 open-memex 来说，这篇几乎就是一份故障定位手册：解析、切片、检索、重排、生成，每一层都对得上记忆管线的环节。

**叙事主线**：先点出初学者的选型误区（还没处理过几份真实文档，就开始比 Qdrant 和 Pinecone、LangChain 和 LlamaIndex），再把 RAG 拆成两条链路（离线索引、在线查询），用两个企业例子说明"上游丢的东西，下游换再强的模型也找不回来"，接着给出分层故障定位的六个问题和"语义相似 ≠ 业务相关"的关键概念，按问题选技术（SQL、GraphRAG、Agentic RAG 各有各的用处），最后落到评测基线和职业建议：能让 AI 写出 RAG 系统，和能独立诊断、评估、优化 RAG 系统，是两种能力。

## 精读

### 文章怎么说

**1. 别掉进选型陷阱**

还没有处理过几份真实文档，就开始研究 Qdrant 和 Pinecone 哪个更好，LangChain 和 LlamaIndex 应该选哪个，Embedding 模型的 Benchmark 谁排名更高。花了几个星期研究工具，最后还是不知道自己的 RAG 系统为什么会回答错误。

**2. 两条链路**

一个典型的 RAG 系统可以拆成两条链路：

- **离线索引链路**：数据获取、文档解析、清洗、切片、向量化、索引建立。
- **在线查询链路**：理解用户问题、检索相关证据、重排序、组装上下文，再交给大模型生成答案。

理解这两条链路之后，很多工程问题就会变得清晰。

**3. 两个例子：上游丢的东西，下游找不回来（示意例子，作者举例说明，非真实事故报告）**

- 一家企业的采购制度中，不同金额的采购订单对应不同的审批流程。如果 PDF 解析阶段破坏了表格结构，导致采购金额和审批条件之间的对应关系丢失，那么后面换再强的 Embedding 模型、向量数据库和 LLM，都未必能够恢复这些信息。
- 用户询问最新的报销标准，但知识库中同时存在 2025 年和 2026 年的制度文件。两份文档在语义上可能都非常相关。如果没有时间过滤、版本管理和有效的重排序机制，大模型甚至可以非常忠实地引用原始文档，却给出一个完全错误的业务答案。

所以 RAG 系统的准确性，并不是一个单纯的模型能力问题，而是整条数据链路共同作用的结果。

**4. 分层故障定位：最值得培养的能力**

当系统出现错误时，逐层问六个问题：

1. 正确的信息是否存在于原始数据中？
2. 解析之后是否被完整保留？
3. 切片有没有破坏语义？
4. 检索阶段是否召回了正确证据？
5. 重排序有没有错误地淘汰关键文档？
6. 最终传递给模型的上下文是否完整？

只有确定问题发生在哪一层，才能知道应该优化什么。而不是每次遇到错误，就不断修改 Prompt、更换模型、增加检索数量，最后整个系统越来越复杂，却没有真正解决问题。

**5. 语义相似不等于业务相关**

"支持退款"和"不支持退款"，在向量空间中可能具有较高的相似度，但两者的业务含义完全相反。这也是为什么企业级 RAG 往往需要结合 BM25、向量检索、元数据过滤和 Reranker，而不是单纯依赖 Embedding。

**6. 按问题选技术，不是按流行度选**

- 对于结构化业务数据，直接使用 SQL 查询可能比向量检索更准确。
- 对于关系密集型知识，可以考虑 GraphRAG。
- 对于需要不断补充证据、动态切换信息源的研究任务，Agentic RAG 才可能体现出优势。

这些技术都不是必须使用的标准配置，而是针对不同问题的解决方案。

**7. 评测：没有基线，你不知道自己在优化还是在添乱**

没有固定的测试集，你根本不知道今天更换一个 Embedding 模型，明天修改 Chunk Size，后天增加一个 Reranker，究竟是在优化系统，还是单纯增加了系统复杂度。比较合理的方式，是先准备几十道具有明确参考答案和证据来源的问题，建立最基础的 RAG 评测基线，再逐步改变单个主要变量，比较 Recall@K、答案准确性、证据忠实度、响应延迟和实际调用成本。有时候你可能会发现，优化原始数据质量所带来的收益，比更换一个更强的大模型还要明显。

**8. 职业建议：Demo 会跑 ≠ 交付完成**

现在借助 Codex、Claude Code，搭建一个完整的 RAG Demo 已经不是特别困难的事情。但一个人能够让 AI 写出 RAG 系统，和一个人能够独立诊断、评估和优化 RAG 系统，还是存在很大的区别。对于想往 AI Engineer、FDE 方向发展的人，真正值得投入时间的，是从头到尾做一次真实的 RAG 项目，把遇到的每一个问题、每一次技术决策、每一次评测结果都记录下来。先证明最简单的方案能够解决什么问题，再通过数据证明为什么需要引入更复杂的方案。不要把技术栈的丰富程度当成工程能力，也不要把一个能够运行的 Demo 当成已经完成的业务交付。框架只是实现手段。真正的 RAG 工程能力，是知道系统为什么能够找到正确的答案，也知道它找不到正确答案的时候，应该去哪里解决问题。

### 附录：Brij 的七层技术栈（转引，仅供参考，未经核实）

恩宇转引的 Brij Pandey 指南把 RAG 拆成七个模块：大模型、RAG 框架、向量数据库、数据解析、模型托管、Embedding、系统评测；推荐的入门组合是 OpenAI + LlamaIndex + Chroma + Docling + Ollama + OpenAI Embeddings + RAGAS。Brij 的原话是"不用先精通七层再动手，先搭一个小的，再逐层升级"。这份清单是通用入门推荐，恩宇的论点恰恰是别从选型开始——所以这份清单在这里只当附录，正文的价值在恩宇的评论，不在 Brij 的选型表。

### 证据不支持什么

- **采购表与报销版本两个例子是示意例子**：作者举例说明机理，不是真实事故报告，没有出处、没有数据。
- **Brij 的七层选型清单未经核实**：LlamaIndex、Chroma、RAGAS 等推荐是 Brij 的个人经验，没有经过我或恩宇的验证；按恩宇自己的论点，这份清单本来就不该是起点。
- **没有给出任何实测数据**：Recall@K、答案准确性、证据忠实度、延迟、成本都是方法建议（"应该这样比"），不是某次实验跑出来的数字。
- **"分层故障定位"没有展开到操作层**：六个问题是诊断框架，但每层具体怎么查（比如切片坏没坏怎么看、重排序错没错怎么验），文章没写——这是留给读者自己的功课。

### 小沐的分析与判断

**这篇最值钱的是"分层故障定位"六问。** 它跟 #62《Who Verifies the Verifier?》是同一个思想的不同落点：#62 说评分器要拆成看得见的缺点检测器，这篇说 RAG 出错要拆成看得见的六层——都是"把黑盒拆成能定位的层"。也跟 PingPilot 的 Tier 1 + Tier 2 是同一路数：先分层，再逐层验收。

**跟清单里已有两篇 RAG 的关系**：#25《Agentic RAG》是 Agentic RAG 一种形态的专篇；#60《RAG 评测》是评测的专篇（三种失败模式、评测机制）。这篇新加的东西有四样：两条链路的框架、分层故障定位六问、"语义相似 ≠ 业务相关"、SQL / GraphRAG / Agentic RAG 的选型决策树。重叠的部分（评测基线、Agentic RAG 只是选项之一）跟 Stone 之前对 #25 的判断一致——Agentic RAG 不必另成一层，它是按问题选用的工具之一。

**直接对上 open-memex**：记忆管线的每一层都能对上这篇的六问——解析（文档进库时结构保没保住）、切片（语义切没切断）、检索（R@1 / MRR 是检索侧实测版）、重排序（rerank 会不会淘汰关键记忆）、生成（Faithfulness / Correctness 是生成侧缺的另一半）。#60 评测篇里记过的"过期记忆 = 旧版政策"正是这篇报销例子的翻版：没有时间过滤和版本管理，模型会忠实地引用旧记忆、给出错误答案。评测集最该先补的 case，#60 里已经写了（"记忆已更新、旧记忆还在库里"），这篇给了它一个更一般的说法。

**对上 Helix 和 PingPilot**：Helix 的 context 阶段（知识透明化）要的就是这篇讲的东西——知识怎么进来、每层保没保真；PingPilot 的上下文层同理。恩宇说的"先证明最简单的方案能解决什么，再用数据证明为什么需要更复杂的方案"，跟 PingPilot V1.5"规则先行、主模型判断、需要升级就升级"的方向是一致的。

**一个保留**：文章对"怎么建评测集"只给了一句话（几十道题、有明确参考答案和证据来源），没展开——题怎么选、证据来源怎么定、多久更新一次，都没写。这是下一步可以追问的地方，也是 open-memex 评测集真正要啃的活。

### 职业启示

对 AI Solutions Architect / FDE 这个方向，这篇划了一条线：Demo 会跑 ≠ 交付完成。能让 AI 写出 RAG 系统是起点，能独立诊断、评估、优化才是工程能力。FDE 的价值正在这条线后面——客户的系统出问题时，你要能定位到层、拿出数据、证明改动有效，而不是换个模型再试一次。这也是 P4 叙事里"组织级 SME"的落点之一：不是你会用的工具多，是你能讲清系统为什么对、错在哪一层。
