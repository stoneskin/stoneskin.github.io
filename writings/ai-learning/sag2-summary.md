# SAG2 详细摘要：无 embedding 多跳检索，BM25 + Jev 在查询时现找现连

> 来源（一手原文）：Yuchao Wu《SAG2: Embedding-Free Multi-Hop Retrieval with BM25 and JEV》，arXiv:2610.22588，2026-10-15，Zleap AI。论文：https://arxiv.org/abs/2610.22588 ；评测代码：https://github.com/Zleap-AI/SAG-Benchmark

## 1. 核心机制：三样东西，分工写死

SAG2 只有三样东西：一个 SQLite 数据库、BM25、Jev。分工是论文 §1 定死的——本地词项索引管“便宜地捞候选”，Jev 管“在上下文里判证据”，两者在查询时才碰面（Abstract、§1）。

```
问题 q
  │
  ▼
[SQLite FTS5 + BM25] ── 捞前 100 个候选段 (B=100)
  │
  ▼
[Jev · Noul 是非题] ── 每段一个 0–1 概率：“这段是不是必需证据？”
  │                     （第 1 轮无上下文；后几轮带上已捡到的证据一起判）
  ▼
取前 10 段当种子 (s=10) ── 从其正文挑 20 个扩词 (L=20)
  │                     （词的权重 = 种子内频次 × 全库稀有度 × 与原问题的句内重叠 × 种子分数）
  ▼
用扩词再 BM25 捞一轮新候选 ── 回到 Jev 再判
  │
  ▼
最多扩两轮 (H=2)，共三轮打分，输出前 100 段；前 10 再按多样性重排
```

### 1.1 索引：只存原文和词项，不算向量（§3.1）

每段存来源、标题、正文和到原始基准段落的映射，进 SQLite FTS5。分词用 Jieba（加拉丁连词处理），去停用词；标题、 headings、正文字段的 BM25 权重是 (2,2,1)。相邻段落拼到约 2,200 字符封顶。入库 = 文本处理 + 写索引，**没有 embedding 计算、没有模型抽取**。语料标题别名和词项文档频率都在本地算，不调模型。

### 1.2 Jev 那道题到底怎么问（§3.2）

这是全文最关键的一段，值得逐字把握。对候选段 d，第 r 轮的分数是 s_r(d) = J(q, d; E_r)，J 是 Jev 的 Noul 接口，E_r 是当轮的共享已捡证据。问法是：**这段本身是否提供了完整回答链里必需的一个事实，包括中间识别事实**——实体身份和关系约束必须尊重；已捡上下文能建立连接，但只出现在上下文里、候选段自己没有的事实，不能算到候选段头上；光是沾边、光是背景，不够；不许用外部知识推理。输出只当排序分用。

第一轮 E_0 为空；扩一轮后，上下文 = 已保留的扩种 + 新捞候选的前 10；最后一轮用上一轮排名前 10 段加它们暂定的旧分数，让 Jev 对照着重判一遍。上下文里只有捡到的文本和模型输出，没有标准答案、没有标注。

### 1.3 扩词与候选保留（§3.3–§3.4）

每轮打分后，取分数最高的 10 段没扩过的当种子。扩词权重的四项（§3.3 公式）：种子内频次（取对数）、全库稀有度（IDF 式）、所在句与原问题的词重叠、种子自身的 Jev 分数（归一化后压到 0.5–1 之间，低分种子降权不丢弃）。取前 20 个词。

扩的时候，每个词单独捞一串没见过的段，词内用 BM25 排（扩词必含、原问题词不强制含——新段可以靠桥接词进来，原问题词只影响排序）；各词的串按词优先级交错合并，凑满 100 个新候选。注意：**决定下一轮排名的是 Jev 分数，不是这次 BM25 分**。

### 1.4 有界流程与开销上限（§3.5）

默认最多扩两轮（H=2），三轮打分；没词、没种子、没新候选就提前停。最后一轮只准进最多 20 个新段，其余位置留给已打过分的旧段重判。每道题最多判 340 次（含重判），这是配置上限，不是 HTTP 次数、token 数或耗时的上限。实现用 Python + SQLite FTS5；Jev 经 OpenRouter 的 Noul 接口调用，实验用的版本是 typesafe/jev-1.13-20260917（§4.3）——注意，我们 10 月查到 OpenRouter 上架的是 jev-1.14，论文实验用的是 1.13 的 20260917 快照。

## 2. 数据：每组数字的口径

评测口径（§4.1）：MuSiQue、2WikiMultiHopQA、HotpotQA 各取官方开发集 1000 题子集，语料是该子集的支持段 + 干扰段拼起来的池子。Recall@k 是捡到的支持证据占全部支持证据的比例；AllEvidence@k 是整套证据全进前 k 的题占多少。**只评检索，不评最终答案生成。**

### 2.1 三个多跳基准（§5.1，表 1）

| 方法 | MuSiQue R@10 | 2WikiMultiHopQA R@10 | HotpotQA R@10 |
|---|---|---|---|
| BM25 | 54.41% | 71.50% | 86.90% |
| BGE-Large-EN-v1.5 | 64.08% | 73.75% | 93.35% |
| NV-Embed-v2 | 77.27% | 80.75% | 97.70% |
| HippoRAG 2 | 73.76% | 93.40% | 97.15% |
| SAG（上一代） | 83.37% | 93.57% | 97.70% |
| **SAG2** | **86.62%** | **97.43%** | **99.00%** |

SAG2 的 R@5 和 R@10 在三个基准上都是第一；比 SAG 高 3.25 / 3.86 / 1.30 个点，比 BM25 高 32.21 / 25.93 / 12.10 个点。MuSiQue 的完整证据覆盖率 AE@10 从 BM25 的 17.40% 涨到 69.50%。但 SAG 在 MuSiQue 的 R@1、R@2 上仍更高（36.82% / 63.62% 对 34.30% / 62.18%）——作者自己的解读：SAG2 的优势在“能给读者好几段”时更明显，单段命中不是它的强项。

### 2.2 企业文档基准（§5.2，表 2）

EnterpriseRAG-Bench：511,962 份合成公司文档（消息、邮件、工单、会议记录、文档），470 道有标注文档的问题，按源文档去重后取前 10。SAG2 文档 Recall@10 是 **81.10%**，已发表的 BM25 基线 68.4%、向量基线 46.0%、Bash Agent 55.8%。分题型：项目相关 83.58%、完整性 76.24%、受限类 96.67%，但**语义类只有 58.40%**——纯靠词项搭桥，语义 paraphrase 仍是短板。作者也注明：基线用的是各自发表的检索实现与评测管线，Bash Agent 的输出预算不同，这组对比只讲检索表现，不等同于算力预算相同或端到端答案质量相同。

### 2.3 三组消融：功劳到底是谁的（§5.3，图 4；附录 A）

都在 MuSiQue 同 1000 题上：

- **扩几轮**：只判不扩（BM25+JEV，H=0）R@10 是 67.93%；扩一轮到 83.36%（+15.43 点，95% 区间 [14.09, 16.81]）；扩两轮到 86.62%（再 +3.26 点）。扩一轮少用 36.29% 的判次，是更便宜的工作点。最终输出里，有 389 道题的支持段根本不在最初前 100 里——扩确实捞到了新证据。
- **同样判次，不扩行不行**：把一轮 BM25 池子放大到判次与 SAG2 相当（329,194 对 331,325 次），R@10 只有 69.82%，比 SAG2 低 16.80 点。结论：光把候选池放大，补不回“带上下文扩”的好处。
- **共享上下文**：去掉共享证据，R@10 从 86.62% 跌到 76.25%（−10.37 点），AE@10 从 69.50% 跌到 52.20%。上下文不只是排序调料，它决定下一轮扩什么。
- **按跳数拆**（附录 A 表 A3）：两跳题 R@10 92.86%、AE@10 87.07%；三跳 85.34% / 62.34%；**四跳 69.58% / 28.31%**。第二轮扩对四跳题的增益最大（+6.17 点），但四跳的完整覆盖率仍只有不到三成——长链是已知最弱的一环。

### 2.4 索引与查询成本（§5.4，表 3）

MuSiQue 全库 11,656 段：建索引 2.36 秒，SQLite 文件 25.87 MiB，离线模型调用 0 次、0 美元。查询时模型费：前 100 题 0.433769 美元，1000 题 4.326379 美元（不含机器租金与答案生成）。在线延迟没报——作者明说服务等待时间没从并发执行里拆出来。

## 3. 增量：相比已读材料，新的是哪一点

- **对决策模型与 Jev（组一）**：新的是“用法”。10 月那份总结讲了 Jev 的三题型、价格、实测画像和“当前置过滤器”的定位；SAG2 把 Noul 用在了检索循环中间——每轮判、判完决定扩什么、带着已捡证据再判。过滤器是一次性的，SAG2 的裁判是循环里的。
- **对 SAG（上一代，arXiv:2606.15971，§2、§4.2）**：SAG 用 LLM 把每段抽成事件 + 实体，存 MySQL，dense 向量存 Elasticsearch，查询时 SQL join 共享实体的事件。SAG2 把这两样全砍了：不抽事件实体、不算 dense 向量，连接改成“段 → 词项 → 段”，判断改成 Jev。代价是 R@1/R@2 略输 SAG，换来的是准备成本归零。
- **对 HippoRAG 2**：同样做多跳图检索，HippoRAG 2 是离线用 LLM 抽实体关系建好知识图谱、查询时 Personalized PageRank 走图；SAG2 是离线什么图都不建，连接只在查询时发生。SAG2 在三个基准的 R@10 上都赢了它（86.62 / 97.43 / 99.00 对 73.76 / 93.40 / 97.15）。
- **对 Karpathy《LLM Wiki》（第 49 份）**：同一道题的两个答案。LLM Wiki 是“一次编译进 wiki，越用越富”——预先投入；SAG2 是“查询时现算现连，绝不预投”。你的系统里热记忆与冷记忆可以各取一边，不必二选一。
- **对 Agentic RAG**：Agentic RAG 的循环是检索→评估→决定回答还是重试；SAG2 是同一循环在证据层的实现——评估（Jev 打分）直接决定下一轮检索什么，而不是只决定“要不要再试一次”。

## 4. 证据不支持什么

这一节是参谋口径，作者没说的、流行解读多说的，都列在这里：

- **“JEV = Junction Edge Value”不支持。** 这是二手文章的展开，论文全文没这么写。论文里 JEV 就是 TypeSafe 的 Jev 决策模型，引用的是 Almeida 2026《Introducing System One Models & Jev》和 TypeSafe 官方文档（§1、参考文献）。“交点/连接点”那个意象来自上一代 SAG 的动态超边（query-time dynamic hyperedges），不是 SAG2 的 JEV。
- **二手文章的 8.36%→52%→61.48% 不支持。** 论文表 1 里 BM25 在 MuSiQue 的 R@10 是 54.41%，不是 8.36%；SAG2 最终是 86.62%（MuSiQue R@10），不是 61.48%；“超最佳 encoder 5%”也对不上表 1 的口径（SAG2 比 NV-Embed-v2 高 9.35 个点，比 SAG 高 3.25 个点）。这组数字的指标、子集、k 值全都没写清，引用请用 §2 的表。
- **“RAG 已死”不支持。** 论文只评检索、不评答案生成（§4.1 明说），没测端到端问答； dense 方法在 R@1 上并不弱；语义类问题 SAG2 只有 58.40%。它证明的是“轻量准备 + 查询时判断”在多跳证据召回上能赢，不是对 RAG 的死刑判决。
- **“完全离线、零成本”不支持。** 离线零成本只限建索引（§5.4）；查询时每次都要调 hosted Jev，问题和候选段都要发给服务方（§5.5）。作者自己把这列为首要部署局限：Jev 的架构、参数量、权重当时都不公开，公共访问只走 hosted API；因此即便索引在本地，系统也不能完全在本地独立部署，外部处理被禁的地方用不了。本地可部署的决策模型是作者点的下一步，但精度与资源需求都还没测。
- **“SAG-Wiki 装上就能用”未核实。** 二手文章给的 `pip install sag-wiki` 安装命令，我在 PyPI 与论文里都没核实到；论文给的唯一代码出处是评测仓 SAG-Benchmark，已确认的包名是 `zleap-sag`。照抄安装命令之前，先去仓库核对。
- **泛化还没证实。** MuSiQue 在方法开发时就用过（§5.5），三个基准都是固定开发子集；EnterpriseRAG-Bench 的语料是合成的；词项检索仍会漏掉 paraphrase、别名和没有词项连接的证据；四跳完整覆盖率 28.31%。作者也承认：实验只证明了整套系统的表现和扩/上下文的贡献，没孤立每个词权重因子的作用，也没证明 Jev 比其他决策模型更好。

## 5. 小沐的分析与判断

［本节是小沐自己的判断，不是原文内容。］

- **最值得偷的不是 BM25，是“判断前移”的分工。** 检索系统历来把“懂语义”这件事放在准备阶段（算向量、抽实体、建图），SAG2 把它整个搬到查询时，只留一个便宜的词项索引在本地。这个分工成立的前提只有一个：判断必须便宜、快、且只输出概率——Jev 恰好同时满足三点（70–500ms、输出免费、$0.042/百万输入 token）。换一个要写长推理的模型当裁判，这套循环在成本上立刻就垮了。所以 SAG2 与其说是检索论文，不如说是给决策模型找的第一个“杀手级用法”：判断便宜到可以每轮都判，系统结构就可以跟着变。
- **但它把命脉交给了别人。** §5.5 的坦白很关键：Jev 权重不公开、只能走 hosted API、问题与候选段都要外发。这对 open-memex 是直接冲突——你的立场是 local-first 即边界，记忆内容不外发。SAG2 的架构可以借，分工可以借，Jev 本人不能照搬进记忆系统，除非哪天有了本地可部署、精度相当的决策模型（10 月总结里那条 DIY 路线：Qwen3.5-0.8B + 决策头 + LoRA，5070 上 42 分钟，正是为这一天准备的）。
- **数字上最诚实的三处是消融。** 扩一轮 +15.43 点、去上下文 −10.37 点、同判次不扩只到 69.82%——这三组数比表 1 的第一名更有信息量，因为它们回答了“钱到底花在哪”。如果以后要在 open-memex 里试，先抄的应该是“带共享上下文扩一轮”这个工作点（少 36% 判次，只丢 3.26 点），而不是全开两轮。
- **四跳 28.31% 是给你的提醒。** 你的记忆查询里，真正难的也是三跳以上的链（人 → 项目 → 决策 → 原因）。SAG2 在这上面也没办法，说明“词项搭桥”有天然天花板：链越长，中间段与原问题的词重叠越弱，桥就越难搭。长链问题可能还是得靠预先编译的那一极（LLM Wiki），或者 SAG 式的实体抽取回来补——论文 §5.5 末尾自己也留了这个口子。

## 6. 术语台账

| 原文词 | 一句白话 |
|---|---|
| SAG2 | 本文的系统：SQLite + BM25 + Jev，无 embedding 多跳检索 |
| SAG | 上一代：事件–实体 + SQL join + dense 检索，MySQL + Elasticsearch |
| JEV / Jev | TypeSafe 的决策模型；这里只用 Noul（是非题 → 0–1 概率） |
| Noul | Jev 的是非题型：问一个是非问题，回一个概率 |
| BM25 | 经典关键词排序：词频 × 稀有度，SQLite FTS5 自带 |
| Recall@k / R@k | 前 k 段里捡到的支持证据占全部支持证据的比例 |
| AllEvidence@k / AE@k | 整套证据全进前 k 的题占多少（比 Recall 更严） |
| Expansion / 扩 | 用已捡好段的词再捞一轮新候选 |
| Seed / 种子 | 每轮分数最高的前 10 段，供词扩下一轮 |
| Query-time association | 连接不在入库时建好，只在查询时动态发生 |
| FTS5 | SQLite 的全文检索扩展，BM25 由它提供 |

## 附录 A. Abstract 中文全译

［忠实翻译；原文口径见正文各节。］

强多跳检索应当做到易于部署，而不需要昂贵的语料准备或复杂的数据基础设施。我们提出 SAG2，一种无 embedding 的检索架构，围绕单个 SQLite 数据库、BM25，以及来自 JEV 的上下文证据判断而构建。SAG2 遵循 SAG（SQL 检索增强生成）的查询时关联原则，同时用原始段落上的词项索引取代了它的事件–实体索引与 dense 索引。被选中的段落提供词语，供进一步检索；新捡到的证据指导后续判断。这把语义证据选择移到了查询时，消除了离线 embedding 计算、基于 LLM 的事件–实体抽取，以及专用数据库服务器。由此得到的系统兼具轻量准备与强检索精度：在 MuSiQue、2WikiMultiHopQA 与 HotpotQA 各 1000 题的子集上，SAG2 在所比较的方法中取得了最高的 Recall@5 与 Recall@10，Recall@10 分别为 86.62%、97.43% 与 99.00%。它在 511,962 篇文档的 EnterpriseRAG-Bench 语料上还达到了 81.10% 的文档 Recall@10。为全部 11,656 段 MuSiQue 段落建索引只需 2.36 秒，生成 25.87 MiB 的数据库，不需要任何模型调用。SAG2 证明，准确的多跳证据检索可以由紧凑、快速准备的基础设施支撑，成为知识检索应用的实用基础。

## 附录 B. 按你的要求：职业启示

［长期要求：学习类材料附职业启示节，每条挂得住原文证据。］

- **给客户讲检索选型时，你现在有了三选一的坐标。** 以前讲 RAG，选项基本是“向量库选哪个、切块多大”；SAG2 给了第三个坐标：准备成本（索引 2.36 秒、25.87 MiB、零模型调用，§5.4）对查询成本（每千题 4.33 美元 Jev 费）对长链能力（四跳 AE@10 28.31%）。FDE 交付时，这张三维取舍表比“我们用了向量库”更有说服力——客户要的是“为什么是这个组合”，不是“用了什么时髦件”。
- **“判断便宜了，结构就能变”是可迁移的设计直觉。** SAG2 的结构创新不是新算法，是判断单价降下来之后，分工跟着挪了位置（§1）。做 AI 落地评审时，这是一条能直接用的提问：这个系统里最贵的判断是哪一个？如果它便宜十倍，哪个环节可以从准备阶段挪到查询时、哪个预建的索引可以不建了？PingPilot 的 alarm triage 里也有同样的位置：先判“是不是真问题”的裁判如果足够便宜，静默与建单的分工就能重排。
- **部署边界是 FDE 必须先问的问题，不是事后补的。** SAG2 的首要局限是 hosted 依赖（§5.5）：权重不公开、问题与候选段外发、外部处理被禁的地方用不了。企业客户（尤其金融、保险）第一句就会问这个。以后给客户推任何“轻量本地索引 + 云端判断”的组合，先把“什么数据出了内网、经过谁的手”这张表画出来，再谈精度数字——精度是第二句，边界是第一句。
