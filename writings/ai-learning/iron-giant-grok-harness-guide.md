## 一句话结论

大多数 Grok Bot 配置让一个贵模型包办写入、路由、判断、批准和自查，所以凌晨 3 点会变慢、变贵、行为怪异。能长期稳定跑的配置把工作分成四层：Grok 负责写、Jev 负责决策、Harness 负责强制执行、Swarm 负责扩展——贵模型只干它最擅长的写作，决策这种量大、格式固定的活交给便宜得多的专用模型。

## 为什么值得看

- **Agent = 模型 + Harness，这句等式直接对上我们的设计**：PingPilot、WorkBuddy、harness-landing 三处都在补同一课——模型本身不是系统，让模型守规矩的脚手架才是。这篇把脚手架拆成了可照抄的六件套。
- **决策与写作拆开，是最实在的省钱办法**：Agent 循环里多数步骤不是写作，而是决策（选文件、选模型、能不能跑、做完了吗、留还是丢）。这些调用交给贵模型、还以散文形式返回，是最贵又最没必要的部分——Jev 的做法是把决策变成类型化问题，返回带概率的类型化答案。
- **合同、关卡、交接三件套，与我们的设计一一对应**：每个 Bot 的五字段合同、对每条主张的证据标注、任务结束的 HANDOFF.md，分别对应 PingPilot 的 plan contract、Tier 1 确定性检查 + Tier 2 Verifier、session 持久化与交接。
- **10 个提示词拿来就能搭**：从装 Chief、立合同、三道关卡、Merge Bot 到周五审计，顺序就是搭建顺序，作者建议当晚先搭 Chief。
- **一句话就值回票价**：“填不出 FORBIDDEN，就说明这个角色还没想清楚。”——禁做事项不是装饰，是角色定义合不合格的试金石。

## 叙事主线

1. 现状：大多数 Grok 机器人配置由一个模型包办写入、路由、判断、批准和自查——于是凌晨 3 点变慢、变贵、行为怪异。
2. 出路不是换更强的模型，而是分层：能长期稳定运行的配置把工作分成四个层次——Grok 写、Jev 决策、Harness 强制执行、Swarm 扩展。
3. Harness 先行：运行循环、可触达工具、记忆位置、禁做事项、检查方式——agent 是模型加 harness，不是模型本身。文中以 Cursor 用同一模型处理 835 页 SQLite 手册、改用新 Harness 后合并冲突从 70,000+ 降至 1,000 以下为例。
4. 决策层单拎出来：Agent 循环中多数步骤是决策而非写作；Jev 是 TypeSafe AI 的 System One 模型，发送状态加类型化问题，返回带概率的类型化答案，无散文。
5. 算账（作者的数，见文末警惕）：一次路由决策，Grok 4.7 约 $0.0049，Jev 约 $0.000084，约便宜 58 倍；每天 1 万次决策约 $49 对 $0.84。
6. 扩展靠 Swarm：一个 Chief、几个专家团队、一条共享总线；按瓶颈而非按应用雇人，先 Chief + 一个专家，排队了再加。
7. 三个实例走完全流程：收件箱分流、内容引擎、代码 Swarm——每个实例都落在同一个骨架上（研究、写作、决策、关卡、合并、批准）。
8. 收尾的检查清单：加第二个 Bot 之前先确认七件事；每周五 16:00 跑一次审计，统计、收紧一条规则、退休一个 Bot。

## 精读层

### 四层分工

| 层 | 干什么 | 用什么 | 成本形态 |
|---|---|---|---|
| Grok（写） | 写代码、草稿、计划 | Grok 4.7（文中价格 $2/$6 每百万 token） | 按量，最贵 |
| Jev（决策） | 路由、评分、是-否判断 | jev-1.13.0（文中价格 $0.042 输入每百万、输出免费） | 极低 |
| Harness（管） | 合同、关卡、交接、日志 | /workspace + Skills | 一次性时间成本 |
| Swarm（扩） | 并行专家与合并 | Grok Bot + Cursor Cloud Agents | Bot 越多 token 越多，需缓慢增加 |

结论是昂贵模型仍在循环中，只是不再为每个小决策付费。

### Harness 的六件套

1. **Chief**：只路由、不执行。分流、选专家、写任务文件、等 HANDOFF、汇总三行；仅在涉及金钱、发布、删除、签名或对外可见内容时上报。
2. **每个 Bot 的五字段合同**：工作（job）、来源（sources）、判断（judgment）、输出（output）、禁做（forbidden）。填不出 FORBIDDEN，就说明角色没想清楚。
3. **/workspace 以文件代替聊天保存上下文**：research、drafts、evidence、approvals、handoffs 五个目录；上下文在文件里，交接不断线。
4. **Source、Evidence、Action 三道关卡**：来源关（每条主张标出处）、证据关（每条主张标注 VERIFIED / INFERRED / UNKNOWN，Jev Noul 核查，低于 0.7 丢弃）、行动关（发送、发布、付款、删除、签名先做草稿放 /workspace/approvals 等批准）。
5. **每个任务结束时的 HANDOFF.md**：固定格式——任务、状态、产出路径、来源、下任负责人、决策、不确定项、不得假设项。没有 HANDOFF 文件，即任务未完成。
6. **用户自己掌握的 ACTION_LOG.md**：所有合并与行动记一笔，审计的底本。

### Jev：决策层

- **三种问题类型**：Choice（选择）、Score（评分，1–5）、Noul（是/否，返回 0–1 概率）。
- **价格与延迟（作者所引）**：每百万输入 token $0.042，输出免费，端到端延迟 70–500 毫秒。
- **阈值即纪律**：破坏性 Noul > 0.5 时挂起审批；Choice 置信度 < 0.75 时上报 Chief；证据关 Noul < 0.7 丢弃；Shell 命令风险 Noul > 0.2 即等用户；Merge Bot 处 Jev Noul 高于 0.3 的改动上报。
- **最先迁移到 Jev 的 5 类决策**：选文件、选模型、是否可安全运行、是否完成、保留还是丢弃。
- **调用规矩**：Grok Bot 在决策前先把 Jev 请求写成 /workspace/decisions/[step].json 并执行 /workspace/tools/jev.py，引用 Jev 的数字而不转述——决策留痕，不留在聊天记录里。

### Swarm 的五条规则

1. 按瓶颈而非按应用雇人。
2. 先 Chief + 一个专家，工作排队时再加。
3. 团队通过 /workspace + 一个线程沟通，不做长聊天。
4. 代码交给 Cursor Cloud Agents 在隔离 VM 中执行，Grok Bot 对结果负责。
5. 一个中立 Merge Agent 落地工作：只处理 /workspace/approved 队列、不写功能、确认测试与证据关、公正解决冲突、所有合并记入 ACTION_LOG.md。

一个账号最多可有 50 个 Bot 与群聊合计。

### 三个实例

- **例 1 收件箱分流**：每小时读邮件，Jev 回答团队（Choice）、紧急度 1–5（Score）、是否需人工先看（Noul）；仅紧急度 ≤ 3 且 Noul < 0.3 时由支持 Bot 起草回复，其余进 /workspace/approvals；Chief 在 9:00 和 17:00 各发一次汇总。
- **例 2 内容引擎**：研究 Bot 收集来源、写作 Bot 只依据来源起草、Jev 从清晰度、证据、钩子三项 1–5 评分，任一项低于 4 打回一次，第二次失败则挂起，最终由用户批准，不自动发布。
- **例 3 代码 Swarm**：Grok Bot 任技术负责人，把工单拆为可独立测试的最小单元，每个单元启动一个 Cursor Cloud Agent，Jev 检查每条 Shell 命令是否会删除或覆盖数据，Merge Bot 落地 PR，不可逆操作由用户批准。

### 检查清单与 10 个提示词（功能清单，不逐字贴原文）

加第二个 Bot 之前需确认：Chief 先于专家存在；每个 Bot 有五字段合同；/workspace 已有 research、drafts、evidence、approvals、handoffs；决策走 Jev、写作走 Grok；每个对外操作有三道关卡；有一个 Merge Agent 和一份 ACTION_LOG.md；默认静默、仅在异常时通知。

10 个提示词各管一件事（按搭建顺序）：1 装 Chief；2 给每个 Bot 立合同并要求复述；3 决策前先写 Jev 请求文件再执行；4 HANDOFF 文件固定格式；5 三道关卡；6 Merge Bot；7 收件箱分流流程；8 内容引擎质量关；9 代码 Swarm 流程；10 每周五 16:00 的审计——统计 Jev 决策与散文决策、Jev 平均置信度、空跑的例程、等待超过 4 小时的审批、在文件夹外写作的 Bot，并建议收紧一条规则、退休一个 Bot，未经用户同意不改动。

## 跟 PingPilot / WorkBuddy / harness-landing 的咬合

- **Chief ≈ 我们的路由层**：PingPilot 的 Analyzer（只读判断）+ Decider 简化方向（规则先行、主模型判断、需要升级就升级），WorkBuddy 的 brain 调度，都是“只路由、不执行”的 Chief——这篇给了 Chief 的最小职责清单（分流、选专家、写任务文件、等交接、汇总三行、只在五类事上上报）。
- **五字段合同 ≈ plan contract**：PingPilot 的 plan 与 session 工具契约缺的正是 FORBIDDEN 这一栏——“填不出禁做事项，角色就没想清楚”，这句话可以直接当合同评审标准。
- **三道关卡 ≈ 我们的三层验证**：来源关 + 证据关 ≈ Tier 1 确定性检查（主张须有出处与证据标注）+ Tier 2 Verifier（独立第二意见）；行动关 ≈ human on the loop（发送、发布、付款、删除、签名先做草稿等人批）。
- **HANDOFF.md ≈ session 持久化与交接**：PingPilot 的 session 设计（session id、步骤幂等、断点续跑）要回答的正是同一个问题——任务做到一半断了，接手方凭什么继续；固定格式的 HANDOFF.md 是最轻量的答案。
- **ACTION_LOG.md ≈ 审计日志**：WorkBuddy 的审计目录与 Pack 准入、PingPilot 的 override 率统计，都需要这份“所有行动记一笔”的底本；没有它，评测与复盘都没有材料。
- **Jev ≈ 决策便宜化的通用解**：thinktank 的 judge 成本、PingPilot 每 case 约 $0.07 的成本账，都在付同一笔钱——让贵模型做散文式决策。Jev 的解法（类型化问题 + 概率答案 + 阈值升级）不依赖 Grok 生态，可以平移到任何“便宜模型做路由、贵模型做执行”的地方。
- **Swarm 的 Merge Bot ≈ 中立合并**：多 agent 并行写代码最后总要有人合并；一个不写功能、只确认测试与证据关、公正解决冲突的中立角色，比让某个专家顺手合并干净。
- **要警惕的三处，不要照搬**：
- 作者的数字（合并冲突 70,000+ 降至 1,000 以下、58 倍、$49 对 $0.84）是文中自述，未独立验证；引用时标明是作者的数。
- Jev 是 TypeSafe AI 的产品（hosted 模型），用它等于引入一家厂商依赖；SAG2（第 28 份）里 Jev 也是 hosted、非完全离线——同一条提醒。
- 价格是 2026-11-17 的快照（Grok 4.7、jev-1.13.0），模型与价格都会变；阈值（0.5、0.75、0.7、0.2、0.3）是作者的经验值，不是测出来的数，照搬前先在自己的量上跑一遍。
