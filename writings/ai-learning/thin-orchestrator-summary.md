# Meta《The Thin Orchestrator》总结：让路由器少做事，Agent 反而更可靠

> 原文：Meta Engineering 博客，2026-10-19
> https://engineering.fb.com/2026/10/19/ml-applications/thin-orchestrator-ai-agent-architecture/
> 场景：Meta 推荐系统的数据列接入（data column onboarding），跨 3 个代码仓库、3 种语言、最多 6 个管道阶段必须保持同步

---

## 一、问题：上下文越多，表现越差

第一版是"一个聪明 agent 装下全部知识"：10+ 数据源的配置 schema、代码生成规则、管道路由逻辑、验证要求全塞进一个 agent。Demo 里没问题，上生产开始幻觉：

- 把 A 子系统的字段命名规范套到 B 子系统上
- 用错数据源的代码生成模式（cross-contamination，概念互相污染）

引用的研究（Mount Sinai 预印本）：80 个任务的批量下，多 agent 编排系统准确率 65.3%，单 agent 只剩 16.6%，且 token 用量最高降到 1/65——作者归因于任务隔离防止了上下文干扰。

另一个对照：单 agent 靠工程师逐任务手写定制 prompt，能到 70–80% 成功率；不手写就掉到 10–20%。结论：**这不是 prompt 工程问题，是架构问题。**

---

## 二、解法：1,300 行编排器，零领域工作

系统拆成两层：

**编排层（确定性路由器）**：1,300 行，路由 20+ 工作流。不推理代码、不生成配置、不碰代码库，只做分类意图、收集字段、可靠性检查、委派。固定 7 步协议：

1. Read：读目标子 agent 的指令文件
2. Check：查目标是否已存在（防重复）
3. Gather：向用户收集必需字段
4. Auto-discover：自动推断能推断的（仓库类型、已有配置）
5. Reliability gate：检查活跃警告 / 必需 reviewer
6. Delegate：带全上下文委派给子 agent
7. Handle：处理结果，报错或确认成功

第 1–5、7 步全是确定性的；**只有第 6 步涉及 LLM 推理，且发生在子 agent 的隔离上下文里**。

**子 agent 层（14 个专家）**：每个是完整的领域专家，上下文互相隔离。Schema 管理 agent 只懂配置注册表，Population agent 只懂 10 个数据源的代码生成，Validation agent 只懂构建与质量检查。谁都看不到全图——"这是 feature，不是 bug"。

每个子 agent 结构统一：知识源（运行时加载的领域文件，每个几千 token）+ 预收集清单 + 分步工作流 + 仓库发现模式 + 排错映射。第 15 个子 agent 和第 1 个结构一模一样，加新专家是模板活。

**知识文件运行时加载**：25+ 个知识文件按领域组织，编排器不内嵌。文件更新后下一次会话自动生效，不用改编排器、不用重新部署，同一份知识文件还能服务多个平台实现。

---

## 三、关键招数：新用例不造新 agent，只写工作流模板

编排器用 workflow template 定义阶段顺序——确定性状态机，约束 LLM 的决策空间：

- Column Onboarding：Schema → Validation → Population → Testing
- Event Onboarding：Schema → Population → Validation → Testing → Event Processing
- Pipeline Migration：Assessment → Planning → Population → Validation → Monitoring

支持 Pipeline Migration 这个全新用例时，只写了一个新模板、换了个 agent 排序，**新 agent 代码为零**，直接上生产。

---

## 四、结果

- 新列配置准备：手工 3–4 天 → 旧配置驱动系统约 1 天 → 现在不到 1 小时
- 约 2/3 的系统变更无需人工大改直接落地

---

## 五、为什么有效：架构边界对齐计算边界

1. **确定性决策保持确定性**："哪个子 agent 处理" 是路由决策，不是推理任务，别用 LLM 做
2. **上下文隔离防污染**：数据源 A 的 population agent 永远看不到 B 的模式，想幻觉都幻觉不出来
3. **失败被关在局部**：子 agent 挂了编排器重试或升级，失败不污染编排器状态、不串到其他子 agent
4. **每层独立进化**：更好的模型同时提升全部 14 个子 agent；知识文件更新立即生效；新模板解锁新能力不动 agent

反面论证：重型编排器一旦幻觉，错误会扩散到全部下游（路由错、字段错、跳过可靠性检查）。薄编排器的路由和检查不依赖 LLM 推理，几乎没有幻觉空间；创造性发生在下游隔离的领域上下文里，风险最小、失败可控。

---

## 六、给任何团队的 5 条应用原则

1. 路由与推理分离：编排器在做领域决策就是做太多了；路由用关键词匹配、意图分类、字段收集等确定性手段，领域推理全推给隔离的子 agent
2. 子 agent 结构统一：知识源、必需输入、执行步骤、错误处理四件套一致，加能力是模板活不是架构活
3. 扩规模靠工作流模板：新用例先问"能不能把已有 agent 换个顺序"，不能复用说明 agent 与用例耦合太重
4. 知识运行时加载而非构建时内嵌：更新即时生效、跨平台复用
5. 确定性/概率性边界画死：每个组件先定性——路由决策（确定性）还是推理任务（概率性）？编排器在一边，子 agent 在另一边，不要混

## 七、跟 Stone 项目的咬合

- **12 步路线图缺口 01（状态机）的生产级样本**：Meta 的 workflow template 就是确定性状态机在真实大厂系统里的样子——编排层不推理，恰恰是可靠性来源
- **thinktank**：陪审团的"分工审议 + judge 汇总"就是薄编排的一种形态——成员在隔离上下文里推理，汇总层不做领域判断、只做聚合与熔断
- **opencode-fuse**：三档路由 + 升档重跑与此同源——路由器只决定"给谁、什么档"，不替模型想问题；升档是确定性规则，不是再问一次 LLM
- **一句话共同思想**：harness 层越克制，模型层越自由；可靠性来自边界，不来自更聪明的 prompt
