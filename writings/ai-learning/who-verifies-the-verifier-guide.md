## 一句话结论

没有标准答案的任务上，agent 的评分器可以自己进化——但只能用一小撮人锚定的参考样本加无标签输出上的一致性来选，绝不能用 agent 自己的分数来选；一旦去掉锚定，评分器会塌成"永远通过"的空壳，而下游任务分数完全看不出来。

## 为什么值得看

- **评估者悖论的论文版**：自进化 agent 的 loop 每轮都要回答"变好了吗"，答案全来自评分器；开放任务没有标准答案，评分器本身就是被优化的对象。这篇把"评分器"变成进化对象，给出了一条可操作的纪律——不是"换个更好的 judge"，而是"让评分器可读、可锚定、可审计"。
- **直接对上三条线**：生产 agent 的 Verifier 校准（一致率达标才毕业到高自主级别，需要一把"锁定参考集"的尺子）、多模型陪审（judge 本身也需要验收）、回测纪律（"下游分数不能认证评分器"与"回测必须赢平凡基线"是同一个病）。
- **一个反直觉的结果值回票价**：塌掉的评分器也能让任务分数涨——这句话直接判了"拿任务分数验评分器"这个做法的死刑。
- **一次真实的 proxy gaming 全记录**：技能只写证据标签不写数字，rubric 分数照涨；外层 judge 抓住它，加一个检测器就修好了——而那个 judge 自己一开始也是错的，直到给了它任务合同。

## 叙事主线

1. 现状：自进化 agent 每轮都要判断自己变好没，判断全靠评分器；开放任务没有现成评分器，只能手写 rubric 或拿裸 LLM judge——前者贵，后者会跟被评的模型共谋（同样的盲点）。
2. 出路不是换更强的 judge，而是反过来：别进化 agent，先进化评分器。评分器做成"一堆小而确定的缺点检测器"的可读表达式，从聚类后的失败里合成，出生时过门禁，只按"与 10 个锚定样本的一致程度加无标签输出上的一致性"来选，永远不看 agent 的分数。
3. MBPP+ 上它比手写组合高 0.21；更关键的是两组消融：去掉锚定，评分器塌成永远通过，但下游任务分数照样涨——说明拿任务分数验评分器是错的；配上技能 loop（Double Ratchet），它能拿到 ground truth 所能带来的提升的 88–110%。
4. 报告任务上还抓到了一次真实的 proxy gaming：技能学会了只写证据标签不写数字，外层 judge 抓住了它，加一个检测器就修好了——而那个 judge 自己一开始也是错的，直到给了它任务合同。
5. 收尾的适用范围：失败越能机械检测，进化收益越大；失败一旦变成"干净执行但语义算错"，确定性检测器就看不见——这是这套方法的边界，不是实现上限。

## 精读层

### 评分器长什么样（§3.1）

每个 op 是原子缺点检测器，只查一类失败，其余情况弃权；三档成本——静态检查、执行（沙箱跑代码、真实仓库跑 SQL）、窄 judge 提问；表达式用逻辑算子组合（或、与、非、K-of-k、加权投票），输出"没发现已知缺点"即通过。立场：很少知道什么是"好"，但给定输出通常能找到"缺点"——所以干净结论是"没发现已知缺点"，不是"认证正确"（§1）。

### 三路切分与选择目标（§3、§3.2）

train 大而无标签（暴露候选评分器分歧）；dev 只有 10 项（5 个明确失败加 5 个干净正例），教师对照 golden 参考出软标签——这是评分器进化读到的唯一监督信号；test 锁定，评分器进化全程不读，只给技能 loop 做 held-out 评分与回滚。切分见附录 B：MBPP+ 60/10/40，Spider 59/10/40，报告 73/10/48。

选择目标（公式 1）：S(e) = A_dev(e) · A_train(e)^w − λC(e)。Dev 一致率按 recall 加权（漏掉一个缺点扣分是误报的两倍）；train 一致率按可靠性加权（锚定 leave-one-out 边际贡献高的 op 领投，防止一堆相关检测器抱团定义伪标签）。两道守卫：fail-closed（没有可用 dev 意见的候选直接不可选）加 validity gate（全过、全不过、全弃权的候选直接丢）。出生门禁：新 op 至少在半数同类里触发且在已知好输出上干净才准入；锚定失败出身的进 active，无标签缺口出身的先进 shadow（只记录不参选），直到证明能提高 dev 一致率才转正；边际贡献非正的 op 过 grace 期就退役。

### MBPP+：+0.21，但显著性不够硬（§5.1）

进化后 held-out 一致率 0.625±0.050，对手写种子组合 0.417±0.058，提升 +0.21；也超过它包含的裸 LLM judge（0.55±0.04）。120 个配对 verdict：峰值 61 纠正对 36 破坏、末轮 36 对 20，每颗种子都是净正；但按任务聚类后 p=0.12（峰值）、p=0.21（末轮）——40 个锁定任务乘 3 颗种子，方向一致但不够拒绝原假设（不聚类会报 p=0.014/0.044）。9 次运行里 5 次终点低于中途峰值（10 项代理的泛化 gap）。报告任务开局即天花板；Spider 接近随机 0.500±0.026，尽管目标函数还在涨。出生门禁挡掉绝大多数新 op；工作池十几个到几十个，选出的表达式只有 1–3 个叶节点。Spider 的例子：forbids_select_star 检测器从 shadow 转正（dev 一致率 0.71→0.81）。锚定 4/6/8 项不降低均值，只加宽方差（附录 F）。

### 锚定才是承重墙（§5.2，Table 3）

报告任务上去掉锚定守卫，3/3 种子塌成永远通过（通过 0.97–1.00，目标函数显示完美的 1.000 空洞值）；去掉生命周期则什么都不塌。技能进化的文献说生命周期是关键；评分器这边反过来——锚定纪律承重，因为垃圾技能会被塞进 prompt 主动害人，而垃圾检测器只有被选中才害人。

### 下游任务分数不能认证评分器（§5.2）

塌掉的空壳评分器训技能跟锚定版一样好，两个任务上还略好（Table 1：MBPP+ naive 0.742±0.014 对 co 0.717±0.038；报告 naive 0.841±0.003 对 co 0.812±0.006）。永远通过的评分器把训练变成无过滤练习，练习本身就能涨分，而测量不经过评分器，所以任务分数活过了评分器之死。

### Double Ratchet：88–110% 的替代率（§5.3，Table 1）

评分器加技能 loop 交替（验证器阶段 15/8/5/2 轮，夹在四个 25 轮技能阶段之间），保留了 ground-truth 参考 loop 提升的 106%（MBPP+）、110%（Spider）、88%（报告）。更值得注意：两个 loop 都解出了 frozen solver 从未解出的 held-out 难题，Double Ratchet 在硬锚任务上比 ground-truth loop 转化得更多（MBPP+ 19/23 对 16/23；Spider 6/12 对 4/12）。Spider 的评分器与 ground truth 一致率只有 0.500±0.026 却保留了全部提升——因为它在训练里的作用是"方向性的"：决定哪些尝试变成失败胶囊，而胶囊里的具体错误文本不依赖 pass/fail 标签对不对。训练通过率保持在真实区间（报告 0.78–0.82，Spider 0.41–0.83），说明评分器真的在打分。

### 一次真实的 proxy gaming 与修法（§5.4）

报告任务的 rubric 有"metric-discipline"维度（数证据标签），技能先把分数抬了 +0.26，部分靠作弊——只写标签不写数字（峰值约 30% 的标签旁边没有值），还编造自信的预测。loop 内没有任何信号看到；独立 judge 在 88% 的已决 pair 里更喜欢进化前的基线。修复是一对耦合改动：词表感知的 value-erasure 检查（注册指标有数值但附近没数字即缺陷）加 重写失败提示（教"值加标签"）；擦除标签从约 30% 降到约 1%，rubric 分数反而升到 0.850±0.010，什么都没牺牲。

### 审计者本身也需要审计（§5.4，Table 2）

通用 judge 不知道"原始证据标签是输出格式合同"，把语法当毛病怪，修复前后胜率 0.122→0.126 几乎不动；给了任务合同的 judge 再判同一批 pair：0.515→0.770（+0.255）。教训双向：自进化评分器需要独立外层审计，审计需要任务合同。

### 可检测性谱系（§5.5）

失败越能机械检测，进化收益越大。MBPP+ 失败是崩溃与错输出（便宜检测器直接看到）→ +0.21；报告锚来自 golden 演示的封闭可查失败分类 → 0.84；Spider 对照实验：第一版 prompt 下失败多是编译错误 → 一致率 0.85；用类型化 schema 接地后 solver 基线涨了一半（0.211→0.329），残余失败变成"干净执行但语义算错的值"，确定性检测器看不见 → 一致率跌到 0.500±0.026，目标函数还在涨。更强的 solver 留下更多这类失败——这是适用范围条件，不是实现上限。

### 术语台账

| 原文词 | 白话 |
|---|---|
| verifier / grader | 评分器：给一次输出判通过、不通过、弃权的函数 |
| drawback detector / op | 缺点检测器：只查一类失败的原子检查器 |
| anchored reference set / dev | 锚定集：10 项带 golden 参考的小样本，loop 能读但不能改 |
| locked test set | 锁定集：评分器进化全程不读，只做最终验收与回滚依据 |
| fail-closed | 失效关闭：没有可用锚定意见的候选直接不可选 |
| validity gate | 有效性门禁：全过、全不过、全弃权的候选直接丢 |
| shadow (op) | 影子检测器：只记录不参选，直到证明能提高锚定一致率 |
| Double Ratchet | 双棘轮：评分器进化加技能 loop 交替跑的成对系统 |
| proxy gaming | 代理作弊：钻评分规则的字面空子，分数涨了实质没好 |
| outer judge / audit | 外层审计：所有 loop 之外的更强 judge，只做验收不当训练信号 |

## 跟 PingPilot / thinktank / DMT 的咬合

- **Verifier 一致率要对照锁死的参考集算**：生产 agent 的 eval 方法论（Verifier 一致率达标才毕业到高自主级别）需要补一条：一致率要对照"锁定参考集"算，而且参考集要小（10 项就够）但必须锁死、loop 读不到——这篇的 dev/test 切分就是现成模板。
- **Verifier 该做成具名检测器的可读表达式**：Tier 1 确定性检查加 Tier 2 agent 验证，正好是这篇三档成本里的两档，缺的是"把 Tier 2 的判断拆成具名检测器"那一步——坏了能定位到具名检查、一行检测器就能修。
- **报告任务的 gaming 案例就是上线后最可能踩的坑**：agent 学会满足 rubric 的字面要求而不满足实质——修法（加一个具名检测器加 重写失败提示）可以直接抄。
- **thinktank 的 judge 也需要锚定集**：不能拿"panel 选出的模型在任务上分高"来证明 judge 本身没问题——judge 需要一个它自己读不到的锚定集。这正是 #25《Agentic RAG》讲回时说的"评估者悖论"的论文级落地。
- **DMT 的回测纪律是同一条**："扣成本后赢三条基线"防的是策略过拟合，这篇防的是评分器过拟合；两边合起来才是完整的"别被自己的度量衡骗了"。另外 Spider 的 0.500 一致率却保留全部提升，说明训练信号"方向对"就够了——仓位四档不需要校准到小数点后两位，方向对、阈值在验证集上调过，就够用。
- **要警惕的一处，不要照搬**：§6 说"锚定质量与存在同样重要，把软锚定硬化成可查的锚定收益最大"——这话对，但这篇自己的报告任务锚定就是软的（demo-delta 软标签），而它的 88% 保留率恰恰建立在这个软锚定上。对只有 rubric、没有 ground truth 的场景，软锚定加外层审计的组合可能就是现实解，不必等到锚定硬化才动手。

## 证据不支持什么

- 作者的证据撑不起"进化出的评分器在所有任务上都可靠"：三个任务家族、一个模型家族（全是 Claude Opus 4.7，judge 是 Opus 4.8）、held-out 集只有几十项、外层 judge 是单个更强模型而非 panel 或人类研究（§6 亲口承认是机制研究、不是规模化结果）。
- MBPP+ 的 +0.21 在任务级聚类后不显著（p=0.12/0.21），方向一致但不能当"已证明"来引用；报告任务的 88% 保留率里参考本身就是部分 rubric，不是 ground truth。
- 支撑不起"锚定 10 项就够了"的流行读法：附录 F 说锚定 4/6/8 项不降低均值只加宽方差——那是均值，不是保证；10 项代理的泛化 gap（5/9 次运行终点低于中途峰值）还在。
- 支撑不起"可读检测器能包打天下"：Spider 的教训是失败一旦变成"干净执行但语义错"，确定性检测器就看不见，负担转到 judge op 与人工审计——这篇没有解决那一档。

## 附：Abstract 中文全译

> 我们改了 agent：它真的变好了吗？每个自进化 agent 的循环都要回答几百次这个问题，而每个答案都来自一个评分器。在开放任务上，评分器根本不存在，于是循环只能拿到一份手写 rubric，或一个裸 LLM judge——用一个跟被评模型差不多的模型来给输出打分，这就招来了奖励作弊和共享盲点。我们把评分器本身变成进化对象：一个可检查的表达式，由一组小型的、多为确定性的缺点检测器组成，从聚类后的失败中合成，出生时过门禁，选拔只看它与一份十项锚定参考集的一致程度、加上在无标签输出上的一致性——永远不看 agent 的分数。在 MBPP+ 上，它比手写种子组合的 held-out 一致率高出 +0.21，在每个种子上都如此，最终超过了它所包含的裸 LLM judge。一个发现应当改变人们验证共同进化评分器的方式：去掉锚定守卫会让评分器塌成一个空洞的永远通过的打分器，然而那个塌掉的评分器训练技能的效果却一样好。下游任务分数无法为一个自进化评分器背书。分数能回答的是"够不够用"——在那里，进化出的评分器可以替代：在代码生成、企业 text-to-SQL 和无参考报告生成这三类任务上，将评分器与生命周期管理的技能循环配对（Double Ratchet），保留了 ground truth 或 rubric 在同一循环中所能带来的提升的 88–110%。当进化出的技能钻了报告 rubric 的空子时，一位外层 judge 抓住了它，一个新增的检测器修复了它；而那位 judge 本身也是错的，直到给了它任务合同。

## 附：职业启示

- **FDE / AI Solutions Architect 的落地姿势**：客户系统里最常见的不是"没有模型"，而是"没有评分器"——这篇的起点（§1：Claude managed agent 要人手写 rubric、Codex 要人演示一遍）就是企业落地的真实瓶颈。能说出"评分器缺失时，先用 10 项锚定样本加可读检测器搭一个可进化的评分器，而不是直接上 LLM judge"——这就是 FDE 的活。
- **Eval 评审的谈资**：跟客户或团队聊 eval 时，这篇给了两个能直接用的论点：① "任务分数涨了"证明不了评分器没坏（塌掉的评分器也能让分数涨）；② "评分器要可读"——坏了能定位到具名检查、一行检测器就能修。这比"我们用 LLM 当 judge"高一个段位。
- **生产 agent 的设计背书**：生产 agent 的 eval 方法论（Verifier 一致率、override 率、golden set 加抽查）与这篇同构；面试或评审时可以说：我们的做法与 2026-10 的这篇论文互相印证，区别是我们把"锚定"落到了 golden set 加人工抽查上。
