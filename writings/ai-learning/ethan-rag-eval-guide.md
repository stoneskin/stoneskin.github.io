## 一句话结论

RAG 系统答错了，最没用的解法往往是直接换个更强的模型。先回答“系统到底错在哪里”——检索层、忠实度、还是内容过期——再用一套能持续验证的评测机制去改。会搭 RAG，只是学会了如何让 AI 使用知识；会评测 RAG，才开始真正掌握如何判断 AI 是否可靠。

## 为什么值得看

- **三种失败模式分得干净**：同一个“答错了”，可能是没找到、找到了却胡编、没胡编但引的是旧版——三种错修法完全不同，不分清楚就只能瞎调 Prompt、加检索数、换模型。
- **评测不是仪表盘，是机制**：这篇不讲“打个分做张图”，讲的是评测集、分离测量、逐条记录、回归验证一整套——这正是 open-memex 0.11.0 要补的纪律。
- **Evals 是清单三处深度押注之一**：FDE 落地方法、Agent 跑稳、Evals 体系——这篇是 Evals 那处里最贴自己项目的一篇，直接对着 open-memex 的命中率与回答正确率读。
- **一句话就值回票价**：“忠实于上下文，不等于符合真实事实；回答切题，不等于回答正确；检索命中，也不等于找全了所有证据。”

## 叙事主线

1. 固定流程跑通了不等于能用：准备文档、Chunking、Embedding、向量库、Top-K、Rerank、扔给 LLM、套个前端——一个企业知识库看起来就做出来了。
2. 进业务场景后，“能回答”和“能可靠地回答”是两回事：客户不按 Demo 提问，知识库不可能永远干净；文档会更新、信息会冲突、检索会遗漏、模型会编造，同一个问题换个问法结果都可能不同。
3. 只会搭 RAG 的开发者这时还在改 Prompt、加检索数、想换更强的模型；真正要先做的，是定位错在哪一层。
4. 保修政策的例子：三种完全不同的错（见精读层）。
5. 三个“不等于”：每个指标背后都对应一种系统失败方式。
6. 进生产还缺四问：没答案会不会拒答、版本变了会不会继续引旧内容、不同权限会不会看到不该看的、每次优化带来多少提升和多少成本。
7. 所以最值得重视的是 Evaluation——不是让另一个 LLM 打个 0 到 1 的分做张 Dashboard，而是持续验证系统质量的机制：评测集、分离测量、逐条记录、回归验证，还要接受“新东西加进去可能退化”这个事实。
8. 分界线：demo 开发关注能不能跑通；真正的 AI Engineering 关注能不能稳定运行、能不能被验证、出了问题能不能定位、能不能交付给客户。会把“回答准一点”“幻觉少一点”这类模糊要求翻译成明确评测标准、可复现实验、持续迭代流程的人，才是有价值的 AI 应用工程师。

## 精读层

### 9 个指标（Gauri Tripathi 原推文 + 指标图）

| # | 指标 | 测什么 | 口径 |
|---|---|---|---|
| 1 | Context Precision | 找来的上下文有多少是相关的 | 相关块 / 找来的总块数，越高越好 |
| 2 | Context Recall | 该找的信息找全了吗 | 找到的相关块 / 全部相关块，越高越好 |
| 3 | Context Relevance | 找来的文档与问题的相关程度 | 越高越好 |
| 4 | Faithfulness | 答案有没有检索证据支撑，有没有编造 | 越高越好 |
| 5 | Answer Relevance | 答案切不切题 | 越高越好 |
| 6 | Answer Correctness | 答案对不对（对照标准答案 / 事实） | 越高越好 |
| 7 | Hit@K | 前 K 条里至少有一条相关吗 | 1（有）或 0（没有），越高越好 |
| 8 | MRR | 第一条相关结果出现得有多早 | MRR = 1/N · Σ 1/rank_i，rank_i 是第 i 个问题第一条相关结果的排名，越高越好 |
| 9 | Human Evaluation | 人判有用性、准确性、 grounded 程度 | 标准：Correctness、Helpfulness、Grounding、Completeness |

检索质量（1、2、3、7、8）与生成质量（4、5、6）分开测，9 是人兜底。

### 三种失败模式（保修政策的例子）

- **检索层错**：根本没找到真正相关的文档，或找来大量无关内容、正确资料排在后面。修法：查 Context Precision、Context Recall、Hit@K、MRR，再去动 Chunking、Embedding、混合检索、Rerank——不是调生成模型。
- **忠实度错**：正确资料检索到了，模型没忠实使用——文档写保修两年，模型自己补成三年。修法：测 Faithfulness，即答案里的事实声明能不能得到检索证据支持。检索再好也保证不了模型不胡编。
- **时效错（最隐蔽）**：模型完全按检索到的资料回答、一个字没编，但检索到的是旧版政策——旧文档写一年，最新政策已改成两年。这时 Faithfulness 很高，Answer Correctness 依然很低。

### 三个“不等于”

- 忠实于上下文 ≠ 符合真实事实（时效错就是证明）
- 回答切题 ≠ 回答正确（Answer Relevance 高，Answer Correctness 可以低）
- 检索命中 ≠ 找全了所有证据（Hit@K 是 1，Context Recall 可以很低）

### 评测机制：四件套

1. **评测集**：有标准答案、有权威来源的测试集。
2. **分离测量**：检索质量和生成质量分别测，别混成一个总分。
3. **逐条记录**：每次问答记下检索结果、引用证据、最终回答、成本、延迟。
4. **回归验证**：改了 Chunking、Embedding、Rerank、Prompt 或模型之后，用同一套测试集重跑——定位问题靠指标，验证改动靠回归。

附带一条：接受退化可能。新技术、新框架、新模型加进去，系统可能在某些场景下变差；没有评测，你根本发现不了。真正的工程优化不是架构图上多几个模块，而是能拿出证据：这次改动解决了什么问题，同时付出了什么代价。

### 进生产还缺的四问

- 模型在没有答案时，会不会拒绝回答？
- 资料版本变化后，会不会继续引用旧内容？
- 不同权限的用户，会不会看到不该看的信息？
- 每一次优化，到底带来了多少性能提升和额外成本？

## 跟 open-memex 的咬合

- **检索侧，你已经有数了**：D79 定 band 0.75 后，R@1 从 0.660 升到 0.702、MRR 从 0.804 升到 0.825——这就是 Context Recall / Hit@K / MRR 的实测版。但 Ethan 提醒：命中 ≠ 找全。0.11.0 的 rerank 不能只盯一个数，要 Precision（找来的有多少相关）和 Recall（该找的找全了吗）一起看；只看 MRR 会漏掉“第一条对了、但关键证据在第十条”的情况。
- **生成侧，是现在缺的另一半**：召回准了，回答是不是忠实引用、有没有编造，要单独测。memory_recall MCP 工具的输出要能被 Faithfulness 检验——答案里的每条事实声明，都能指回一条具体的记忆；指不回去的，就是编造的候选。
- **时效错是记忆系统的翻版**：旧版保修政策 = 过期记忆。open-memex 的记忆会过期，评测集里要有一类“记忆已更新、旧记忆还在库里”的 case，专门测系统会不会继续引用旧内容。这是 0.11.0 评测集最该先补的一类——比再加一个通用 case 更有价值。
- **评测机制就是 0.11.0 的纪律**：rerank 换个模型、embedding 加个门、跨语言 rerank 上线，每改一次，同一套测试集回归验证；每次查询记检索结果、引用证据、最终回答、成本、延迟。没有这套机制，改动是变好还是变坏、是不是只在某些场景下退化，你根本不知道。
- **成本也要记**：每次优化拿出证据（提升了多少）与代价（多了多少 token / 延迟）。open-memex 是本地优先，成本主要是延迟与本地算力——同样要记，记法一样。
- **拒答要进评测集**：库里没有答案时，系统要直说没有，不要编。评测集里要有无答案 case，测的就是“会不会拒答”。
- **阈值别抄**：9 个指标都没有阈值——阈值要从你自己的数据里定。D79 的 band 0.75 就是这么来的：不是抄来的数，是测出来的数。0.11.0 的 rerank 阈值也一样，先测再定。
- **要警惕的一处，不要照搬**：这篇是经验文，无数据、无实验、无评测集搭建方法。它给的是“测什么、为什么测”，不是“怎么搭评测集”。搭建方法（评测集多大、标准答案谁定、回归跑多勤）要你自己在 0.11.0 里定，不能从这篇里抄。
