## 17. AI 时代的新封建分层（一家之言，框架漂亮、预测存疑）（2026-10-15）

读 rick awsb 长推有感。他认为 AI 社会既不是哈耶克式乌托邦也不是数字利维坦，而是倒金字塔的"新封建分层"：顶层算力与能源被"数字领主"垄断，中层知识中介坍塌、只剩靠 AI 杠杆的个体小团队，底层因零成本 AI 内容退化成部落社会。
原文：https://x.com/rickawsb/status/2110464793467584996

三处真东西，记下来：

- **"繁荣但没有定价权"**：中层个体/小团队被 AI 放大后效率暴涨，但剩余价值以 API 费、云租金回流顶层——放大器本身也要交"数字地租"。
- **中层坍塌清单**（法务合规、初级金融分析、常规软件外包、中层管理）：第 14 条"苦活被省掉"的宏观版——被省掉的不只是学习过程，是整整一个就业阶层。
- **底层认知环境恶化**：零成本超写实内容瓦解共同事实基础——第 16 条"AI 会说谎"的社会放大版。

两处存疑：

- "数字领主"可能高估了集中的必然性——开源、蒸馏、小模型本地化一直在拆墙（open-memex 的 local-first 就是这个方向）。大型机时代也预言过计算集中化，结果等来了 PC 革命。
- "1-3 年高墙、3-7 年硬着陆"式的直线外推，历史记录一向很差。

## 18. 野心的四种刻度：Rieseberg 的驾驭者手册（2026-10-15）


读 Felix Rieseberg（Anthropic，做 Claude）《How to be more ambitious: A tutorial for humans with models》有感。
原文：https://felixrieseberg.com/how-to-be-more-ambitious-a-tutorial-for-humans-with-models/

他把用 AI 的野心分四种：Speed（更快干同样的活，略过不讲）、Altitude（抽象层级：从"修这个 crash"上升到"让应用保持无 crash"，问"目标之后的目标"是什么）、Depth（专家级深度：用顶尖从业者的工具和方法，做到连专家都能学到东西）、Range（跨领域：组一支 crew——分析师+记者+编辑+做空者和法务会计组成的红队，让模型去"做"他们做的事，而不是"演"他们）。

与随笔的咬合：

- 这篇文章本质上是"驾驭者手册"——Altitude 对应第 3 条的"意图和方向"，Depth 对应"手艺不能丢"，Range 对应智囊团评审。我的随笔是中文个人版，他是英文方法论版。
- Depth 章节明说 "Use an outside judge —— 不要让模型自己评判自己"：第 4、5 条"用另一款 AI 做 review"已是行业共识级方法论。
- "Insist on the same instruments used by the best"：模型被要求"像专家一样"时往往只换词汇不换方法——嘴上像数据科学家，递来的还是 markdown 表格。呼应第 5 条：漂亮的形式不等于真材实料的方法。审棋的人（第 15 条）要看它用的什么"棋具"。
- 文末心理学 self-efficacy（自我效能感）：相信自己能做到的人真的做得更多；"看别人先做到"（4 分钟一英里 46 天被跟上）、"不知道不可能"（Dantzig 把未解难题当作业）。对第 14 条的反方视角：学习过程被省掉是真的，但 AI 也把"敢想"的门槛打下来了。

两处存疑：作者是 Claude 员工，"模型越来越能处理高抽象层级"多少是卖自家货；例子都假设有数据访问和工程基建，对普通人门槛不低。以及 Speed 被跳过，但现实中 90% 的人只用到 Speed——"野心"本身也是金字塔分布。

## 19. AI native 不是用 AI，而是默认 AI 在场（2026-10-16）


读卡夫卡（@kafkaup）长推有感。他认为 "AI native" 正在变成营销词——就像 cloud native 不是"把软件搬上云"，真正的 AI native 是从一开始就围绕 AI 重新设计产品、流程和解题方式。
原文：https://x.com/kafkaup/status/2110860521008206107

他给的试金石：遇到问题时第一反应从"我怎么做"变成"这件事里 AI 能接哪段"。以及 AI first（先问 AI 工具合不合适）vs AI native（流程默认 AI 参与）的区分。

与随笔的咬合：

- 这个区分照到我自己：我说"去"，剩下的 estimate、执行、验证、收尾全在小沐那，我只做判断和拍板——这已经不是"用 AI 工具"，是把 AI 当默认执行层。AI native 不是态度，是工作流的形状。
- "AI-friendly 的信息格式"那段（自然语言表意图、Markdown 共读、JSON/Schema 传结构、MCP 给 AI 执行）几乎就是 open-memex 的设计文档：想让 AI 可靠干活，先把信息摆成它好消化的形状。
- "context engineering 的本质是让 AI 住进你的环境，而不是你把上下文搬进聊天框"——open-memex 干的正是这个，只不过他从 workflow 角度谈，我从 infrastructure 角度做。

一处纠正（Stone 2026-10-16 亲口）：上面"只在分歧处介入"写得不对。准确的说法是——AI 互相审完之后，最后的结果还是我来拍板。AI 评审是提高输入质量的手段，拍板权始终在人手里，不是"分歧才介入"，是"审完我定"。这比"人当质检员"高一层：质检员是被动把关，拍板是主动担责。

## 20. Agent memory 的六阶段框架：先问为什么需要记忆（2026-10-16）


读卡夫卡（@kafkaup）长推有感。他主张选技术（向量库、图库、塞聊天记录）之前，先问 agent 为什么需要记忆：经验连续、效率、个性化、长期任务跟踪、业务护城河。记忆的核心价值是长期交互的连续性，不是记住一切。
原文：https://x.com/kafkaup/status/2110812455488151766

他给的六阶段：①决定记什么（长期价值、可结构化、个性化影响）②抽取分类（实体/关系/时间/来源/置信度；用户偏好、业务事实、过程结论、任务状态、程序性记忆）③暂存去重合并（防脏数据）④分层存储（短期任务状态放 session，长期偏好放存储，语义检索走向量，关系密集走图）⑤检索（何时查、查什么、查多少；压缩而非硬塞； relevance/recency/来源可靠度/使用频率/业务重要性加权）⑥动态维护（增删改查 + 反思，不然记忆变噪音）。

与随笔的咬合：

- 这套框架 open-memex 基本全覆盖——capture、alias、lifecycle 状态机、retrieval-ablation，每一步都有对应实现。不是追热点，是提前把作业写完了。
- "按业务需要匹配复杂度"是全文最值钱的一句：正是"默认不用 embedding"赌注的理论背书——大部分场景词法+同义词就够，embedding 只在跨语言这种明确缺口上 opt-in。
- 评论区 Zipeng Wu 的好问题（使用频率 vs 业务重要性冲突时怎么排？只提过一次的 deadline 不能被天天聊的偏好挤掉）——正是 D77 feedback-weighted ranking 要解决的。问题比实现先到，但答案已在路上。
- 他列的"好记忆四标准"（准确、检索对、有用、可删除）里，"可删除"最容易被忽视。open-memex 的 forget/supersede 链和"retracted 不可悄悄回 active"（D64）把可删除做成了硬约束——很多 memory 项目没做到，可当差异化讲。

## 21. Vibe Coding 的四个习惯：模型是公共品，harness 是护城河（2026-10-16）


读 Kxians（@xulijian1994）长推有感。他的论点：Vibe Coding 玩久了，真正影响效率的不是模型多强，而是自己的使用习惯。四条：①别重复造轮子——先让 AI 搜 GitHub 成熟方案；②定期换对话窗口——一个 chat 用到底会压缩失忆、偏离目标，2-3 个独立功能或几次压缩后就换，前提是文档+持久记忆；③别让 AI 无脑读整文件——先搜关键词/目录/索引，只读相关的，省 token 少污染；④定期"蒸馏"历史（他说最有价值）——让 AI 分析对话史，高频任务做成 Skill，常犯错误写进 AGENTS.md，经验结晶成项目约定。
原文：https://x.com/xulijian1994/status/2110615259979649507

与随笔的咬合：

- 第四条就是"修进 harness"的中文版——只不过别人是建议，我是被纠正一次当晚落地。AGENTS.md、脚本、skill，就是在挖这条河。
- 第二条的评论区补充（chaim chen）：交接文档别写成总结墙，只留四项——当前目标、已确认结论、未解决的报错、下一步怎么验证。compaction 摘要该学这个：摘要不是越全越好，是"接得上"才好。
- 第一条对应 Karpathy 第二条"简单优先，先查是不是已经有了"——野生的经验和 Karpathy 的原则长到一起去了。
- 他结尾最狠："模型大家都能用，但每个人积累出来的工作流，差距可能会越来越大。"

## 22. 原则越短，模型越要聪明：pstack 的"工程原则"压缩（2026-10-16）


读邵猛（@shao__meng）转述 poteto（Cursor 官方插件 pstack 作者）的长推有感。核心洞察：模型越强，给 agent 的指令越该从"冗长的步骤"压缩成"短的、有名字的原则"——每条 10-20 行，是蒸馏出的好实践，不是工作流脚本。
原文：https://x.com/shao__meng/status/2110976920343171542

关键机制有四：①原则是超 mini skill，poteto 预期大部分 skill 最终压缩成短原则或被删掉；②/poteto-mode 让 agent 在多步任务前先读原则索引，事后必须点名"哪条原则影响了哪个决策"（Principles Named or Used），引用无决策=挂羊头卖狗肉，推理可检查；③原则来自真实纠正——她今年纠正 agent 的会话里沉淀出来的"结构化教训"；④原则可单独调用（/principle-<name>），也可当转向 shorthand（"subtract before you add" 直接让 agent 先删过期 adapter）。

Uncle Bob 背书：pstack 是把经典工程智慧（最小改动、先减后加、验证根因、非法状态不可表示、幂等）重编码给 AI agent。

与随笔的咬合：

- "structured sediment of lessons"就是"修进 harness"——AGENTS.md 每条后的"（2026-10-15 抓包…）"是同一个东西。她产品化了，我的是私房配置。
- 压缩方向验证 A/B 拆分：A（原则）越短越硬，B（实现）越具体越好。原则给聪明模型看，实现给笨环境看。
- "老智慧的 agent 化转译"是个富矿：Karpathy 四原则、Uncle Bob 清单，逐条转成 10-20 行 skill。

一处存疑（评论区 @DistillX_AI）：原则越短，对模型理解力要求越高——压缩的前提是模型够聪明，这是条件不是无条件真理。
